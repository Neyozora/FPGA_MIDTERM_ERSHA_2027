# Hardware Memory Format and Address Mapping Specification (Milestone 5)

This document defines the exact binary format, memory ordering, and address
equations for every `.mem` (ModelSim `$readmemh`) and `.mif` (Intel Quartus
Memory Initialization File) generated by `python -m sw.export.export_mem`.

> [!IMPORTANT]
> PyTorch tensors (`OIHW` for Conv2d, `[out, in]` for Linear, `NCHW` for
> activations) are **explicitly converted and verified** against the hardware
> address formulas below. Every exported `.mem` and `.mif` file is read back by
> an independent parser (`sw/export/formatters.py`) and compared element-by-element
> against the source quantized integer arrays (`checkpoints/int8_quantized.npz`).

---

## 1. Two's-Complement Hexadecimal Encoding

All values are stored as unsigned hexadecimal words representing **signed
two's-complement integers**:

- **Signed INT8 (`WIDTH = 8`, 2 hex digits `00`..`FF`):**
  $$
  \text{u8}(x) = x \bmod 256 = \begin{cases} x & \text{if } 0 \le x \le 127 \\ x + 256 & \text{if } -128 \le x < 0 \end{cases}
  $$
  Sign-recovery: if $\text{u8} \ge 128$, $x = \text{u8} - 256$, else $x = \text{u8}$.
  Examples: `+127 -> 7F`, `0 -> 00`, `-1 -> FF`, `-127 -> 81`, `-128 -> 80`.

- **Signed INT32 (`WIDTH = 32`, 8 hex digits `00000000`..`FFFFFFFF`):**
  $$
  \text{u32}(x) = x \bmod 2^{32} = \begin{cases} x & \text{if } 0 \le x < 2^{31} \\ x + 2^{32} & \text{if } -2^{31} \le x < 0 \end{cases}
  $$
  Sign-recovery: if $\text{u32} \ge 2^{31}$, $x = \text{u32} - 2^{32}$, else $x = \text{u32}$.
  Examples: `+1 -> 00000001`, `-1 -> FFFFFFFF`, `-128 -> FFFFFF80`.

## 2. File Format Conventions

### 2.1 `.mem` Format (Verilog `$readmemh`)
- Pure hexadecimal text, **one word per line**, uppercase hex (`02X` for 8-bit,
  `08X` for 32-bit), no `0x` prefix and no comments, so both ModelSim (`vsim`)
  and Quartus synthesis (`$readmemh` in M10K inference) parse them without
  warnings.
- Line $k$ (0-indexed) corresponds to memory address $k$.

### 2.2 `.mif` Format (Intel Quartus Memory Initialization File)
Every `.mif` file contains the five mandatory Quartus declarations:

```text
DEPTH = <number_of_words>;
WIDTH = <8_or_32>;
ADDRESS_RADIX = HEX;
DATA_RADIX = HEX;
CONTENT
BEGIN
    000 : XX;
    ...
END;
```

### 3.1 `conv1_weights.mem` / `.mif` (Depth = 72, Width = 8)
- **Logical index:** `(oc, ic, ky, kx)` with `oc in [0..7]`, `ic = 0`, `ky in [0..2]`, `kx in [0..2]`.
- **Loop order (outermost to innermost):** `oc -> ic -> ky -> kx` (`kx` varies fastest).
- **Hardware address formula:**
  $$
  \text{addr}_{\text{conv1\_w}}(oc, ky, kx) = oc \cdot 9 + ky \cdot 3 + kx \quad \in [0, 71]
  $$

### 3.2 `conv1_bias.mem` / `.mif` (Depth = 8, Width = 32)
- **Hardware address formula:**
  $$
  \text{addr}_{\text{conv1\_b}}(oc) = oc \quad \in [0, 7]
  $$

### 3.3 `conv2_weights.mem` / `.mif` (Depth = 1,152, Width = 8)
- **Logical index:** `(oc, ic, ky, kx)` with `oc in [0..15]`, `ic in [0..7]`, `ky in [0..2]`, `kx in [0..2]`.
- **Loop order (outermost to innermost):** `oc -> ic -> ky -> kx` (`kx` varies fastest).
- **Hardware address formula:**
  $$
  \text{addr}_{\text{conv2\_w}}(oc, ic, ky, kx) = ((oc \cdot 8 + ic) \cdot 3 + ky) \cdot 3 + kx = oc \cdot 72 + ic \cdot 9 + ky \cdot 3 + kx \quad \in [0, 1151]
  $$
  Notice that for a fixed output channel `oc`, the 72 weights needed for one output pixel occupy a **single contiguous address block** `[oc*72 .. oc*72 + 71]`. A sequential MAC engine simply increments its weight ROM counter by `+1` each cycle!

### 3.4 `conv2_bias.mem` / `.mif` (Depth = 16, Width = 32)
- **Hardware address formula:**
  $$
  \text{addr}_{\text{conv2\_b}}(oc) = oc \quad \in [0, 15]
  $$

### 3.5 `fc_weights.mem` / `.mif` (Depth = 160, Width = 8)
- **Logical index:** `(out_class, in_ch)` with `out_class in [0..9]`, `in_ch in [0..15]`.
- **Loop order:** `out_class -> in_ch` (`in_ch` varies fastest).
- **Hardware address formula:**
  $$
  \text{addr}_{\text{fc\_w}}(\text{out\_class}, \text{in\_ch}) = \text{out\_class} \cdot 16 + \text{in\_ch} = \{\text{out\_class}[3:0], \text{in\_ch}[3:0]\} \quad \in [0, 159]
  $$
  Because `FC_IN = 16` is a power of two, the address is pure bit concatenation `{out_class[3:0], in_ch[3:0]}` (zero adders/multipliers in hardware).

### 3.6 `fc_bias.mem` / `.mif` (Depth = 10, Width = 32)
- **Hardware address formula:**
  $$
  \text{addr}_{\text{fc\_b}}(\text{out\_class}) = \text{out\_class} \quad \in [0, 9]
  $$

### 3.7 `test_image.mem` / `.mif` (Depth = 1,024, Width = 8)
- **Logical index:** `(row, col)` with `row in [0..31]`, `col in [0..31]`.
- **Loop order:** Row-major (`row -> col`, `col` varies fastest).
- **Hardware address formula:**
  $$
  \text{addr}_{\text{img}}(\text{row}, \text{col}) = \text{row} \cdot 32 + \text{col} = \{\text{row}[4:0], \text{col}[4:0]\} \quad \in [0, 1023]
  $$
  Because the image is padded to `32 × 32`, the pixel address is simple 10-bit wire concatenation `{row[4:0], col[4:0]}`.
- **Multi-image testbench file (`test_images_100.mem`):** Concatenates all 100 hardware test vectors in order `img_idx in [0..99]`:
  $$
  \text{addr}_{\text{img100}}(\text{img\_idx}, \text{row}, \text{col}) = \text{img\_idx} \cdot 1024 + \text{row} \cdot 32 + \text{col} \quad \in [0, 102399]
  $$
